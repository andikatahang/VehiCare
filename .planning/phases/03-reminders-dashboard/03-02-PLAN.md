<objective>
Build the phase's calculation core: one pure `commonMain` state machine that decides what is due, on which axis, by how much and in what order (D-63), so the card, the rule row, the Detail summary row, the worker and both platforms' notification copy all read the same answer.

Purpose: C-28 exists because six surfaces render "when is this due". If any of them formats or calculates on its own, the dashboard, the list and the notification will eventually disagree — and a reminder that disagrees with itself is indistinguishable from a broken reminder. The machine is also where D-49's honesty rule lives ("no mileage data yet", never an extrapolated odometer) and where D-51's per-cycle silence gets its key.

Output: `domain/ReminderStatus.kt` (`ReminderEvaluation`, `ReminderRow`, `ReminderStatus.evaluate`/`evaluateAll`/`cycleKey`, added beneath plan 01's `DueState`/`ReminderAxis` vocabulary), `domain/ReminderOrdering.kt` (`VehicleReminderGroup`, `ReminderOrdering.sortRules`/`topRule`/`sortVehicles`) and two `commonTest` suites that run on both Android-host and iOS-simulator targets. No resources, no Compose, no platform types, no clock reads: this plan cannot render a sentence and cannot touch the database — it is the only thing in the phase that is cheap to test everywhere.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Stored baseline + user-entered intervals → due state | Corrupt or boundary values (zero, negative, absent) must not produce a fabricated "due" claim on the dashboard or in a notification. |
| Evaluation → delivery | `cycleKey` is the only thing standing between one notification per cycle and repeated nagging (D-51); the worker claims on the exact string this plan computes. |
| "Today" → time axis | The current date enters once, from the caller, so the state cannot silently depend on when the process happened to run. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
