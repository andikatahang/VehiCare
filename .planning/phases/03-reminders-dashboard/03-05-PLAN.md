<objective>
**As a** vehicle owner, **I want to** create, change and remove a reminder rule from a vehicle, **so that** the app knows when that service is next due.

Build the two surfaces that make a rule editable and visible from the vehicle: the single-screen reminder editor (add and edit in one destination) and the Reminders summary row on Vehicle Detail that opens the list plan 04 built.

Purpose: this is the plan where the phase becomes usable end to end for the rule itself — a rule can be created from nothing, read back, corrected and deleted. It deliberately stops before any notification or permission surface: the editor saves and pops, and nothing in it asks for permission (plan 08 adds that hook after the save, which is why this plan's save path must leave a clean, single place for it). The Detail row lands here because it is the entry point that makes the Reminders screen reachable; without it the graph would still have a destination nobody can navigate to.

The editor is a **copy** of the Phase 2 form grammar, not a new grammar: one mutator, an `initialLoadApplied` guard so the database cannot overwrite typing, a one-shot failure flag per snackbar, a single-flight guard on the destructive action, and a pure validation object (written by plan 04) that owns every rule.

Output: `ReminderEditViewModel` and its test, `ReminderEditRoute` (the screen), `ReminderSummaryViewModel` and `ReminderSummaryRow`, the two new graph nodes in `App.kt` plus the Detail entry point, `ReminderEditRoute` in `Routes.kt`, and two Koin ViewModel factories. `RemindersRoute` — declared by plan 04 and deliberately left unreachable — is registered here in the same edit.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Route parameters → repository read | `vehicleId` and `ruleId` arrive as typed route data and must agree before a row may be edited. |
| User text → stored rule | Raw field text is sanitized and gated by the pure validator before it can become a row. |
| Destructive action → database | Deletion is irreversible and must pass the one confirmation dialog exactly once. |
| Failure → user-visible state | A failed write must never look like a successful one, and no failure may leave the form disabled. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-22 | Elevation of privilege | `ReminderEditViewModel` edit load | mitigate | The loaded rule is compared against the route's `vehicleId`; a mismatch resolves to `NotFound`, so a stale or crafted rule id cannot edit another vehicle's rule. |
| T-03-23 | Tampering | numeric fields | mitigate | Every keystroke goes through `ReminderFormValidation.sanitizeKm`/`sanitizeMonths`; `isSubmittable` and `toRule` are the only gate and the only mapper, so a hand-written parse cannot be introduced. |
| T-03-24 | Tampering | `save`/`delete` double invocation | mitigate | `saving`/`deleting` flags gate both methods and every input is disabled while either is set; the destructive path additionally requires the dialog's confirm. |
| T-03-25 | Repudiation | delete confirmation | mitigate | `ConfirmDeleteDialog` is the only call site of `viewModel.delete`, and the success message is hosted on the shell so it cannot vanish with the popped screen. |
| T-03-26 | Denial of service | summary read | accept | The row reads three indexed flows for one vehicle; the result is bounded by the vehicle's own rules, so no pagination is warranted. |
| T-03-27 | Information disclosure | summary/editor content | accept | Only the service type, intervals and due sentence are shown; no cost, note or photo reaches either surface. |
| T-03-SC | Tampering | Gradle dependency resolution | mitigate | This plan adds no dependency and touches no version catalog entry; the phase's single approved install is gated in plan 07. |
