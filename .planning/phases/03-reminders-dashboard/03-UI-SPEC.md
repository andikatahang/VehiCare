# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Stack:** Kotlin Multiplatform + Compose Multiplatform 1.12.1, **Material 3 only** (`material3:1.12.0-alpha03`).
> shadcn / Tailwind / Radix are **not applicable** — the shadcn initialization gate does not apply to this project (KMP, not React/Next/Vite). No component registry is used.
> **Scope of this document:** the visual and interaction contract for the shared (`commonMain`) UI of Reminders and the home dashboard. It **carries forward the Phase 1 design system and the Phase 2 contract unchanged** — no new colour value, type size, weight, radius or spacing step is introduced. The accent token gains **one** new consumer (the checked `Switch` track); `Danger` gains authorised consumers for the overdue due-state sentence and the editor's inline interval error (exhaustive list in §Color).
> **Binding upstream inputs:** `03-CONTEXT.md` D-41…D-65 (user decisions, binding) · `01-UI-SPEC.md` (approved Phase 1 tokens and rules) · `02-UI-SPEC.md` (approved Phase 2 card/chip/form language) · D-01…D-40 carry-forwards · `.planning/research/PITFALLS.md` §§ Notif 1–5, Android 1–4, SQL 2–3 · `.planning/research/ARCHITECTURE.md` § notification scheduling flow.
> **There is no `03-RESEARCH.md`.** This contract is the design source of truth for the phase; everything the phase renders is declared here.

- Body line height is **1.5**; Heading line height is **1.2** (unchanged).

### The due-state grammar — one vocabulary, every Phase 3 surface

Every Phase 3 surface that says when something is due speaks these sentences and nothing else. They are produced by **one pure `commonMain` helper** (proposed `ReminderStatus`, `util/`, with `commonTest` unit tests — the `ServiceDates` / `RupiahFormat` precedent) that returns a structured result (state + driving axis + values); the screen resolves the sentence through the resources below, and the platform notification builders resolve the **same** sentences through their own resource accessor. No surface formats a due state by hand, and no platform has its own wording.

**Axes.** A rule has up to two axes: **distance** (`interval_km`) and **time** (`interval_months`). The state is decided by the axis with the greater urgency (D-46, "whichever is reached first"), and the sentence names **that** axis. The time axis is **always evaluable** (D-49 gives the rule's creation date as the fallback baseline); only the distance axis can be unevaluable ("No mileage data yet").

| State | Distance axis (km) | Time axis | Sentence source |
|-------|--------------------|-----------|-----------------|
| **Upcoming** | `Due in 3.400 km` | `Due on 12 Mar 2027` | `reminder_due_in_km` / `reminder_due_on` |
| **Due soon** (only exists when the rule has a lead window, D-50) | `Due soon — 900 km left` | `Due soon — 20 days left` | `reminder_due_soon_km` / `reminder_due_soon_days` (plural) |
| **Overdue**, including the exact-zero boundary | `Overdue by 300 km` · boundary: `Due now` | `Overdue by 12 days` · boundary: `Due now` | `reminder_overdue_km` / `reminder_overdue_days` (plural) / `reminder_due_now` |
| **Unevaluable** (distance-only rule, and the vehicle has no service entry at all — D-49) | `No mileage data yet` | — (time axis always evaluable) | `reminder_no_mileage_data` |

Rules of the grammar (all binding):
- **Numbers reuse the locked formatters.** Distances render through the mileage formatter (`123.456 km` — dot thousands separators, no unit inside the number; the unit is part of the sentence). Dates render through `ServiceDates.display` (`19 Oct 2026`). Nothing is re-format.
- **Days are whole calendar days** between `ServiceDates.today()` and the due date. `daysLeft == 0` is never "0 days left": it is the **`Due now`** boundary. Day counts use plural resources; distances never do (a formatted quantity has no singular case).
- **The exact-zero boundary belongs to the overdue bucket** (the rule *is* due the moment the interval is reached — D-46), and it renders the worded `Due now`, so the Danger tone always arrives with the word "Overdue" **or** the word "Due now". No fourth state is invented.
- **A rule with no lead window has no Due-soon band** — it travels Upcoming → Overdue. This is the honest behaviour of "notify exactly at due" (D-50).
- **A disabled rule never renders a due state.** Its status line is `Turned off` (see the rule-row anatomy) — disabling silences the rule (D-43).
- The helper is the **only** place the km-vs-days choice is made, so the card, the rule row, the summary row and both platforms' notifications cannot drift.

### Home dashboard — ordering and the card status line (D-57/D-58/D-59/D-60)

**Ordering (D-57 supersedes D-16 for this list):** one `LazyColumn`, one aggregated read per list load (no N+1 — PITFALLS § SQL 3), ordered by these groups, in this order:

1. **Overdue** (including the `Due now` boundary)
2. **Due soon**
3. **Upcoming** (including rules whose only axis is unevaluable — they rank at the **end** of this group)
4. **No active reminder** — vehicles with no enabled rule (none at all, or all turned off): **newest-first, exactly D-16's order**, which is preserved inside this group rather than deleted

The group a vehicle falls into is decided by its **most urgent enabled rule** — the same rule its card displays.

**Ranking inside groups 1–3:** one cross-axis key, `urgency = elapsed / interval` (computed in the axis's own unit — km or days), **descending**. A single comparable number is what makes "3,000 km late" and "14 days late" orderable against each other without a second table.

**Tie-breaks, in order:** (a) the **distance axis wins** over the time axis at equal urgency; (b) lower rule id; (c) vehicle name, case-insensitive; (d) lower vehicle id. Deterministic to the last key, so the list can never reshuffle between two identical loads (PITFALLS § CMP re-sorting).

**The card status line (D-58, D-59, D-60)** — the **only** change to `VehicleCard`, appended as the **last line of the existing text column** (below the plate chip, inside the existing `sm` 8px `Column` stack, so no existing line moves and the 88dp min height is untouched):

- **Content:** `{service type} · {due sentence}` and, when at least one **other** enabled rule is also in the due-soon ∪ overdue set, ` · +N due`. Examples: `Brake service · Overdue by 300 km · +2 due` · `Oil change · Due soon — 900 km left` · `Tire rotation · Due in 3.400 km`.
- **The `+N due` counter** (D-59): `N` = the number of the vehicle's **other** enabled rules in the due-soon ∪ overdue set (the displayed rule is already named, so it is not counted again — `+0 due` therefore never renders; at exactly one due rule the suffix is absent). Unevaluable rules can never be due and never count. Plural-free by construction (`+%1$d due`, no singular form — the counter only renders at N ≥ 1 where a plural would be "1 due" anyway).
- **When the vehicle has no enabled rule:** the line renders **`No active reminders`** (`Body`/`Slate`) — one string for both "no rules" and "all turned off", because it is true in both cases and the Detail screen is where the difference is spelled out. The card is otherwise unchanged.
- **Typography/tone:** one `Text`, `Body` 16sp/400, `Slate` normally and `Danger` when the sentence is an overdue/`Due now` sentence (C-41). `maxLines = 1` with ellipsis — **this line is never allowed to wrap into a second line**, because uniform card height is what keeps the dashboard scannable (D-59).
- **No icons, no badges, no coloured dot, no container fill** — the status is a sentence, never a chip. `Badge` is verified present in the pinned artifact and is deliberately **not** used.
- The line is **inside** the card's merged semantics node (`mergeDescendants = true` is already on the card), so the card is announced as one item ending with its status. The `·` separators are the locked code constant (U+00B7 with single spaces), not a resource.
- A rule whose status line would be `No mileage data yet` renders exactly that sentence on the card — **never** an invented odometer figure (D-49, PITFALLS § Anti-Features: no odometer extrapolation).

### Reminders screen (D-41/D-42/D-43) — `RemindersRoute(vehicleId)`

- `Scaffold` + `TopAppBar("Reminders", back arrow)`; the FAB is the "Add reminder" control (Box-overlaid, 16dp right / 8dp bottom) and stays visible in **every** state (D-19/D-42 precedent).
- **Content:** one `LazyColumn`, `items(rules, key = { it.id })` — keys are mandatory (rows re-order as due states change), `md` 16px horizontal padding, `md` 16px gaps, `3xl` 64px bottom padding (clears the FAB). Rows are ordered **most urgent first**, using the same helper, groups and tie-breaks as the dashboard; disabled rules rank **after** every enabled rule (they cannot be due), newest-first among themselves.
- The **permission status row** (§Notifications off) is the **first item** of the Content state only, `md` 16px above the first rule row.
- No sort control, no filter, no swipe, no long-press. The only gestures are: tap a row (edit), tap its switch (toggle), tap the FAB (add).

### Rule row anatomy — `ReminderCard` (D-43, agent discretion locked here)

The row mirrors the Phase 2 card language and the `ServiceSummaryRow` click technique:

- Container: `Mist`, **12dp** corner radius, `md` 16px inner padding, `heightIn(min = 72dp)`, full content width, built as `Modifier.fillMaxWidth().clip(RoundedCornerShape(12.dp)).background(Mist).clickable(onClickLabel = <cd_edit_reminder>).heightIn(min = 72.dp).padding(16.dp)` — **the exact technique `ServiceSummaryRow` already uses**, so the ripple and the shape are identical.
- **The whole row must NOT carry `mergeDescendants = true`.** It contains a live `Switch`, which must stay its **own** node — merging would swallow the toggle's role and state, and a screen-reader user could no longer flip it. The row's **text `Column` merges** instead, so the three lines are announced as one sentence.
- Row content: `Column(weight 1f, spacedBy 8dp)` then a trailing `Switch` (`sm` 8px gap):
  1. **Service type** — `Title` 16sp/500 `Ink`, `maxLines = 1`, ellipsis. (The stored type string verbatim, D-44/D-40 — no rewriting, no normalisation.)
  2. **Interval line** — `Body`/`Slate`, always present: `Every 5.000 km` · `Every 6 months` · `Every 5.000 km or 6 months` (both axes on one rule read as one interval sentence — "whichever comes first" is the mental model, D-46, and it is stated in words rather than as two rows).
  3. **Due-state line** — `Body`/`Slate`, or `Danger` when overdue/`Due now`: the due-state sentence from the helper, or **`Turned off`** when the rule is disabled. A rule with an unevaluable distance axis renders `No mileage data yet`.
- Trailing `Switch` — **palette-locked (C-33)**: checked track `Ink`, checked thumb `Paper`; unchecked track `Mist`, unchecked thumb `Slate`, unchecked border `Hairline`. Its `contentDescription` is the rule's type (`cd_reminder_switch`, `%1$s reminder` → "Brake service reminder"); M3 supplies the on/off state and role. Never colour-alone: the switch position plus the announced state plus the `Turned off` line carry it.
- Tap on the row (anywhere but the switch) opens the editor in edit mode (`ReminderEditRoute(vehicleId, ruleId)`). The switch toggles `enabled` in place — **one tap, no confirmation** (D-43: disabling is not destructive and loses nothing).
- **Inline due status on the rule row: yes — decided here** (CONTEXT §discretion). Rationale: the phone is where the user checks "when is this due?", and making them open the editor to see the state would contradict the phase's whole point; the state sentence is also what makes the switch's consequence legible.

### Reminder editor (D-42) — `ReminderEditRoute(vehicleId, ruleId = 0L)`

One `Column(Modifier.imePadding().verticalScroll(rememberScrollState()))`, `lg` 24px between field groups, `3xl` 64px bottom padding, **no autofocus** (Phase 2's D-31 discipline: the fast path is tapping chips, not typing). Locked order:

| # | Group / field | Control | Required |
|---|---------------|---------|----------|
| 1 | **Service type** | `Title` section label "Service type" + the **single-select** `ServiceTypePicker` (six presets → learned → "Add custom…") | **`*`** |
| 2 | **Intervals** | `Title` section label "Intervals" + the group hint + two **stacked** `OutlinedTextField`s (`md` 16px apart): "Distance" with `suffix` `km`, then "Time" with `suffix` `months` | **at least one interval** |
| 3 | **Advance notice** | `Title` section label "Advance notice" + the group hint + two **stacked** fields: "Km before", then "Days before" (both optional, no `*`, no suffix — the label carries the unit) | — |
| 4 | **Reminder on** | `ReminderToggleRow`: label `Body`/`Ink` + trailing palette `Switch` (default **on** on add) | — |
| 5 | **Submit** | full-width filled `Button` — "Add reminder" / "Update reminder" | — |
| 6 | **Delete** (edit mode only) | `2xl` 48px break, then the full-width outlined `Danger` button "Delete reminder" | — |

Field rules (all binding):
- **Single-select chip group (C-32).** `ServiceTypePicker` gains `selectionMode: SelectionMode = Multiple` — the **default keeps every existing call site byte-identical**, and the editor passes `Single`. In `Single` mode the first tap selects, a later tap on another chip **moves** the selection, and tapping the already-selected chip is a **no-op** (never a deselect) so the form cannot silently return to an invalid state. Nothing is preselected on add (D-26 carry-forward). Selection is still carried by the `Check` glyph + `Ink` border, never colour alone.
  - **Source-verified limitation (record it, do not "fix" it):** `SelectableChip` in the pinned `Chip.kt` (line 3253) applies `semantics { role = Role.Checkbox }` **inside** the component, after the caller's modifier, so an external `Role.RadioButton` is overridden. A single-select chip group therefore announces checkbox semantics — acceptable because exactly one chip is always selected once the user picks (a checkbox that is always on is not misleading), the requirement is additionally carried by the `*` marker and the disabled submit, and no gesture can leave the group empty. (Verification Notes #3.)
- **Distance field:** numeric keyboard, digits filtered, **max 6 digits**, `suffix` "km" styled to `Label`. **No preview line** (the suffix already names the unit — a second "123.456 km" under the field would be noise); its supporting slot is used only for the error.
- **Time field:** numeric keyboard, digits filtered, **max 3 digits**, `suffix` "months" styled to `Label`.
- **Validation, one rule, one message (C-34):** a field that is **non-blank** must parse to **≥ 1**; a blank field is simply "this axis is not set" and is never an error. The offending field takes `isError = true` and its `supportingText` = **`Enter 1 or more.`** in `Danger` (`Label` role). The same rule and the same message cover the two advance-notice fields (a non-blank advance notice of 0 is invalid; "notify exactly at due" is expressed by leaving the fields empty — that equivalence is spelled out in the hint, not left implicit).
  - Validation lives in a **pure Kotlin object** (the `ServiceEntryFormValidation` precedent): sanitizers (digits, caps), `isSubmittable`, and `errorFor` are unit-tested in `commonTest`. No rule may live inline in a composable.
- **Advance notice (D-50):** optional, per-rule; the group hint states the empty case in words: "Leave empty to be notified only when due."
- **Submit gate (C-35):** enabled **iff** exactly one service type is selected **and** at least one interval is non-blank and valid. The chip group carries **no error line** — its `*` marker and the disabled submit button carry the requirement (the Phase 2 precedent for the service-type group).
- **Saving/save failed/success:** identical to the Phase 2 form — submit shows an M3 `CircularProgressIndicator` in place of its label and all inputs go disabled-but-readable; a failure keeps the form untouched and shows the save-error `Snackbar` with a "Try again" action (one-shot flag); success pops back to the Reminders screen (Flow-driven, the row is already in place and already in order).
- **Back/abandon:** unsaved edits are discarded without a confirmation dialog (Phase 1/2 precedent — that vocabulary is reserved for stored-entity deletion).
- **Edit-mode extra:** "Delete reminder" is the **only** destructive control, below a `2xl` 48px break, and it opens the shared `ConfirmDeleteDialog` — its single call site in this feature. Confirm deletes and pops to the Reminders screen with the shell-hosted snackbar "Reminder deleted."; failure closes the dialog, leaves the editor and the rule untouched and reports the delete-error snackbar. A second confirm while a delete is in flight is dropped (single-flight guard, Phase 1 precedent).

## Motion

Deliberately minimal — Phase 3 ships **no custom animation** (carry-forward):

| Where | Motion |
|-------|--------|
| Screen transitions | Navigation Compose platform defaults (iOS push/pop, Android default). No custom enter/exit transitions |
| Press feedback | M3 default ripple on cards, chips, buttons, rows |
| Switch, dialogs, snackbars, pickers | M3 component defaults only (the `Switch`'s thumb animation is the library's, untouched) |
| Home list re-order | **No** enter/exit or reorder animation when urgency changes the order (e.g. after logging a service, or when a rule crosses into overdue). Existing `key = { it.id }` keeps row state pinned; the reorder itself is not animated (Phase 2 precedent) |
| Reminders list | No appear/disappear animation when a rule is toggled or added; a new row appears immediately |
| Banner / status row | Appears and disappears **instantly** on the foreground permission re-check — no slide-in, no fade, no dismiss animation (a permission state is a fact, not an event) |
| Explicitly banned | Skeleton/shimmer loaders, celebratory animation on save, animated empty-state illustrations, pulsing/attention-seeking indicators on a due state, badge-dot animations, custom hero/parallax transitions |
