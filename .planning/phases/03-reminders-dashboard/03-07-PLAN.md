<objective>
**As a** vehicle owner, **I want to** be notified once when a service comes due, **so that** the reminder I set actually reaches me outside the app.

Purpose: everything before this plan computes and displays; nothing leaves the app. This plan turns a due rule into an OS notification on both platforms, without adding a second database, a second copy layer or a second delivery path: one `ReminderDelivery` orchestrator, one `NotificationScheduler` seam, two thin platform implementations, and a WorkManager worker that runs the same orchestrator the iOS foreground sweep runs — REM-03/REM-04, D-51/D-52/D-53/D-55/D-56.

Output: `commonMain/.../notifications/NotificationScheduler.kt` (permission vocabulary, `ScheduledReminder`/`DueReminder`, the `NotificationScheduler` interface + its 6 members, `createNotificationScheduler`, and the pure `ReminderSchedule`), `notifications/ReminderDelivery.kt` (+`ReminderDeliveryFactory`), `notifications/NotificationTapBus.kt`, two additions to `ReminderCopy`, the Android slice (`NotificationChannels`, `NotificationScheduler.android`, `ReminderWorker`, platform binding, `VehiCareApp`, `MainActivity`, manifest), the iOS slice (`NotificationScheduler.ios`, `IosNotificationDelegate`, `NotificationBridge`, `PlatformModule.ios`, `MainViewController`, `AppDelegate.swift`, `iOSApp.swift`), `AppModule`'s two re-arm/cancel hooks (rules change and vehicle deletion), one `App.kt` sweep + tap route, and two `commonTest` suites.

**Why wave 6.** `App.kt` and `AppModule.kt` are also edited by plan 03-05 (wave 4) and `ReminderCopy.kt` by plan 03-03 (wave 2); shared files are implicit dependencies, so this plan cannot share a wave with either. It additionally needs plan 03-03’s `markNotified`/`ReminderNotificationId` and plan 03-05’s saved-rule path to exist before the sweep can be exercised end to end.

**File count (24), accepted deliberately.** The frontmatter lists 24 files — far above the usual per-plan ceiling — and that is the minimum for this deliverable, not a packaging choice. The seam is atomic: the interface does not compile without both platform implementations, the worker cannot run without the factory, and the iOS delegate delivers nothing until Swift installs it. Any split along those lines lands a wave that is red by construction, and the three tasks already partition the files into seam + Android, iOS slice, and host wiring, so no executor holds more than one slice at a time. `files_modified` is exactly the union of the three task file lists.

**One cycle, two iOS paths, one claim, one armed marker.** iOS delivers a time occurrence from the OS and a mileage occurrence from the foreground sweep, and the OS cannot write `notified_cycle_key` when a pre-scheduled request fires. The orchestrator therefore makes the **cycle** the unit of ownership: it partitions the rows into "immediate" (deciding axis in the immediate set) and "time-owned" (the notification instant is today or past), excludes every immediate candidate from the scheduled list, and never re-arms an overdue cycle. Two persisted facts make the claim honest on both sides of the OS boundary: `notified_cycle_key` says "this cycle has been delivered" and `armed_cycle_key` says "an OS request existed for this cycle". A time-owned cycle is claimed **without posting** only when `armed_cycle_key` proves the OS had its chance; a cycle that was never armed (a rule created inside or after its own window) is claimed **then posted** by the sweep, because otherwise the first notification of a natural first-use path would be silently swallowed. A due-today cycle that is still armed stays unclaimed until a sweep sees it strictly past. That is what makes a single `markNotified` call sufficient on a platform where one of the two delivery mechanisms runs outside the app (D-51/D-53).

**Permission gates the claim, not just the post.** A claim without a possible post would silence the whole cycle: `markNotified` returns `true`, the OS drops the notification because authorization is missing, and every later sweep skips the claimed key. `evaluateAndDeliver` therefore reads `scheduler.permissionState()` **before anything else** and returns on anything other than `GRANTED`, leaving both markers untouched. The grant path re-enters delivery explicitly: `NotificationPermissionCoordinator.requestPermission` calls `scheduler.evaluateNow()` when its callback reports `GRANTED`, so the first add's pre-dialog sweep is harmless and the post-grant sweep is the one that arms and delivers.

**Lead days move the trigger, not the due date.** D-50's `lead_days` is the whole reason a time rule can be "due soon"; scheduling the OS request on the due date would make the field dead on iOS while Android posts at `DueSoon`. `ReminderSchedule.notificationDate` is therefore `currentOccurrence - leadDays` (the due date unchanged when there is no lead), and it is both the trigger date and the time-path boundary. The body is the sentence that will be true when the request fires: `DueSoon(null, leadDays)` for a lead window, `DueNow` for a zero lead. A rule already inside its window when it is created is never armed — it is posted by the sweep with the current day count.

**Recorded limitation (carried, not invented).** iOS scheduling is one pending request per time-based rule, armed on every foreground or rules change and **not re-armed once its cycle's notification instant has passed** (D-51). The one consequence left is deliberate: a user who never opens the app and never logs a service is notified once per cycle, not once per interval, because no app code runs to arm the next request. The former first-cycle gap — a rule created already time-due or after 09:00 on its due date — is **closed** by the never-armed post above, so it is no longer recorded as a limitation. The copy never promises a delivery time (UI-SPEC §Notification content), and Android re-evaluates daily with no such gap. Making iOS schedule N cycles ahead is a copy/contract decision the UI-SPEC does not make, so it is deliberately not implemented here.
</objective>

## Design notes locked before execution

**The seam mirrors `DriverFactory`'s factory shape, but the scheduler itself is an interface.** `commonMain` declares `interface NotificationScheduler` with the six members below plus `expect fun createNotificationScheduler(platformContext: Any? = null): NotificationScheduler`, doing the `platformContext as? Context ?: error(...)` cast on Android. The interface (rather than an `expect class`) is what lets `commonTest` hand `ReminderDelivery` a fake scheduler and assert the permission gate and all three time-path cases; the platform implementations stay `internal` and are named `AndroidNotificationScheduler`/`IosNotificationScheduler`. No `LocalContext`, no Compose dependency, no `Context` in the sibling platform files.

**Six members, and `evaluateNow()` is deliberately not `suspend`:**

1. `suspend fun permissionState(): NotificationPermission`
2. `suspend fun scheduleTimeBased(due: List<ScheduledReminder>)` — declarative: clear this app’s own pending identifiers, then re-add exactly this list. Android’s actual is a **no-op** (its worker evaluates both axes daily, D-52).
3. `suspend fun triggerImmediateIfOverdue(due: List<DueReminder>)`
4. `suspend fun cancel(ruleIds: List<Long>)` — remove both pending and delivered notifications for those rules; the repository hooks call it before re-evaluating so a toggled-off, deleted or vehicle-deleted rule cannot leave a stale banner behind (UI-SPEC interaction rules, D-64). KDoc: iOS matches its own identifiers by the `:r<ruleId>` segment (scheduled) and the `:r<ruleId>:now` suffix (immediate), so no vehicle id is needed; Android cancels `ruleId.toInt()`.
5. `fun evaluateNow()` — non-suspend. The foreground sweep must not be a coroutine a composition can cancel between the claim and the post: a cancelled job there would silence a rule for its whole cycle (the mirror image of D-51). Android enqueues a unique one-shot worker; iOS launches the sweep on its own app-lifetime scope. Callers never await delivery.
6. `suspend fun openNotificationSettings()` — the UI-SPEC requires “denied → straight to the OS app settings”, and only the platform can do that; keeping it here avoids a second expect/actual.

**`NotificationPermission.NOT_DETERMINED` is honest per platform.** iOS reports it (`UNAuthorizationStatusNotDetermined`). Android has no such state — `POST_NOTIFICATIONS` is either granted or not, and the OS never remembers “never asked” — so the Android actual returns only `GRANTED`/`DENIED` and documents that. Consumers that need the first-run distinction (plan 08’s `NotificationPermissionStore`) combine it with their own record of having asked; nothing here fakes a state the platform does not have.

**Claim-then-post, never post-then-claim — with two time-path exceptions that are both claims about what the OS already did.** `ReminderDelivery` is the only place that calls `markNotified` (through `claimCycle`); the two platform implementations contain no claim logic at all. The immediate path claims before building a `DueReminder` and posts only on `true`. The time path cannot claim at delivery — iOS fires the pre-scheduled request with no app code running — so it has exactly three cases, keyed by `armed_cycle_key`:
- **Armed and its notification instant is strictly past:** the OS had its chance; claim without posting, so the sweep cannot deliver a second copy of a cycle the OS already showed.
- **Never armed and its window is already open:** the OS never had it (a rule created inside or after its own window, or a sweep that ran before the first arming); claim **then** post, because a claim-only would silence the entire cycle.
- **Armed and its notification instant is today:** retain the request unclaimed; the 09:00 trigger may still fire, and the next sweep that sees the instant strictly past writes the marker.
Both claim + post pairs (immediate and never-armed time) run inside `withContext(NonCancellable)`, so a stopped worker or a torn-down scope cannot claim a cycle and then drop the notification.

**Two axes, two paths, and the platform names the difference once.** `ReminderDeliveryFactory.create(scheduler, immediateAxes = setOf(DISTANCE, TIME))` carries the default both-axes set (D-52: Android’s worker evaluates both rule kinds); iOS’s `evaluateNow()` calls the same factory with `immediateAxes = setOf(DISTANCE)` explicitly (D-53: time-based sits in the OS scheduler, mileage is manual). `ReminderDelivery` therefore never branches on platform — it filters on the set it was handed. The set means **ownership**, not eligibility: a row is delivered immediately only when the axis that decided its state (`ReminderEvaluation.axis`) belongs to the set. A dual-axis rule whose state is decided by the time axis is therefore left to the OS on iOS even though the rule also carries a distance interval; using the deciding axis instead of the presence of an interval is what closes the cross-path duplicate.

**A cycle is claimed by whichever iOS path owns it, and a claimed cycle is never re-armed.** `markNotified` remains the only claim, and the immediate path still posts only after it returns `true`. The time path cannot claim at delivery, so the orchestrator claims on its behalf in the two cases above, and never re-arms a cycle it has claimed: `scheduleTimeBased` receives only unclaimed rules whose **notification instant is strictly in the future**, plus the already-armed due-today row. `armed_cycle_key` is written only after `scheduleTimeBased` returns successfully, and only for the cycles in that list; it is not a claim and gates nothing except the "did the OS ever have this cycle?" question. A due-today cycle that is already armed is deliberately left unclaimed while its 09:00 request may still fire — the row is excluded from the immediate path by `timePathOwnedRuleIds`, so the late marker cannot produce a second notification, and claiming early would let a second sweep exclude the row and clear the request before it fires. The list stays declarative ("make pending equal this list"), so excluding a rule also clears a trigger armed earlier in the same cycle — the distance-first case. `ReminderSchedule.currentOccurrence` (no rolling) answers "what is this cycle's due date?"; `notificationDate` (occurrence minus `lead_days`) answers "when should the OS speak?"; neither ever rolls forward. On the due/lead day itself the retained request is `today` at 09:00, and the iOS actual refuses any trigger instant that is not strictly in the future, so the request can fire once but an already-fired one can never be resurrected.

**One database.** `ReminderDeliveryFactory.create(scheduler, immediateAxes)` builds `VehicleRepositoryImpl(DatabaseProvider.require())` and `ReminderRepositoryImpl(DatabaseProvider.require(), onRulesChanged = { _, _ -> })`, then constructs `ReminderDelivery(vehicleRepository, reminderRepository, scheduler, immediateAxes = immediateAxes)`. The empty hook is deliberate: the Koin graph’s repository cancels and re-arms on user edits, while the delivery-time repository must not re-trigger the very sweep that is running (a wakeup loop). The factory constructs **no driver** — `DatabaseProvider.require()` is the only read.

**`ReminderDelivery` is absent from the Koin graph on purpose.** Both delivery paths (the worker, the iOS sweep) go through the factory, so the two paths cannot diverge; the graph only contributes the re-arm hook. A second binding would create a third path that no test or device check covers.

**Channel creation is deferred to the notify path, and that is a recorded deviation from plan 03-01’s comment.** The channel needs `notification_channel_name`, a Compose Resource that only resolves through the suspend `getString`, which `Application.onCreate` cannot call. `NotificationChannels.ensureChannel(context, name)` is therefore called idempotently from the Android notify path (RESEARCH Pitfall 6 sanctions exactly this); `VehiCareApp.onCreate` gets an accurate comment instead of a channel call.

**Identifier hygiene without touching plan 03-03.** Scheduled requests use `ReminderNotificationId.encode(vehicleId, ruleId)`. iOS immediate deliveries would collide with a pending request for the same rule, so they append `IMMEDIATE_ID_SUFFIX` (`":now"`); the delegate strips that suffix before calling the strict `vehicleIdOf`, so `ReminderNotificationId` keeps its exact contract and both identifiers still resolve to the same vehicle.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OS notification payload → app | The tap arrives as an `Intent` extra (Android) or a request identifier (iOS) that any other process can forge or replay. |
| worker process lane → database | `CoroutineWorker.doWork()` runs with no Koin container and no Composition, on the same process as the UI. |
| Koin graph → platform module | The Android graph receives a `Context`; the iOS graph receives nothing. A missing or duplicated binding fails at runtime, not at compile time. |
| app → OS notification surface | The notification body leaves the app’s sandbox and appears on the lock screen. |
| dependency graph → build | One new artifact enters the build (`androidx.work:work-runtime`). |
