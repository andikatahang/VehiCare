<objective>
**As a** vehicle owner who just set my first reminder, **I want to** be asked once whether VehiCare may notify me — and to be told plainly when it cannot — **so that** the reminder I trusted the app with actually reaches me.

Purpose: plan 03-07 makes notifications possible; this plan makes them *permitted*. It is the only place in the phase where the app talks to the user about a permission, so it is also the only place that can burn iOS's one-time prompt. D-54 fixes the moment (the **first successful add**, never a launch and never an edit), the order (the rule is saved first), the frequency (at most one automatic explanation per install), and the tone (an in-app explanation before the OS sheet, and denial that costs nothing). D-61 fixes the visible consequence: one surface, two placements, shown only when it is true. Both decisions are implemented here with **one** component, **two** persisted bits and **one** process-wide owner, because the cheapest way to get this wrong is to let the home screen and the Reminders screen each decide for themselves.

**Why wave 7.** `App.kt` is edited by plans 03-05 (wave 4) and 03-07 (wave 6), `RemindersScreen.kt`/`RemindersViewModel.kt` by 03-04, `ReminderEditViewModel.kt` by 03-05, `VehicleListScreen.kt` by 03-06, and the two ViewModel test files by the same plans. Shared files are implicit dependencies, so this plan cannot share a wave with any of them, and it needs plan 03-07's `NotificationScheduler.permissionState()`/`openNotificationSettings()`/`evaluateNow()` to exist before there is anything to read, open or re-enter.

**The askability rule, in full — this is the whole product decision, in one sentence per case.** `NOT_DETERMINED` is always askable. `DENIED` is askable **only** while the app has never yet put the user in front of a prompt (the persisted bit is false) — that is the Android-before-the-first-ask case, because Android has no `NOT_DETERMINED`. `DENIED` after a prompt, and `GRANTED` in every case, are never askable. A surface (banner or row) is shown when permission is simply **not granted** and at least one enabled rule exists. So the surface and the dialog deliberately disagree after a denial: the surface stays (it explains why reminders will not arrive and leads to settings), the dialog never returns (re-explaining an irreversible choice is noise, and the copy already names where to fix it).

**Askability is not the automatic budget — two gates, deliberately separate.** `isAskable` answers "may the OS still be asked at all?"; it is what a **tap** consults, and it never changes on its own. `shouldAutoExplain` answers the narrower question "may the app open this dialog *by itself* one more time?" and is `!hasAutoExplained && isAskable`. The automatic path is spent by the first successful add; a manual tap is not. This is the amendment the user approved on 2026-10-23: the old shape re-offered the dialog on every add and every edit while `notDetermined`, which is the nagging D-54 was written to prevent. `Not now` therefore ends the automatic ask permanently, while the surface's tap still opens the dialog — so a user who deferred is never trapped, only never pushed.

**D-61's tap behaviour — now the decision itself, recorded so no executor re-opens it.** D-61 originally said a tap "leads to the Reminders screen (or to system Settings when permission is permanently denied)". The approved `03-UI-SPEC.md` §"Notifications off" was more specific (askable → the explanation dialog, then the OS prompt; denied → straight to the app's notification settings), and the user **amended D-61 on 2026-10-23** to that two-case behaviour, so the plan and the contract no longer disagree: there is nothing here to re-litigate. The Reminders screen is not addressable from the fleet-level banner anyway (there is no vehicle to open — the banner's subject is the permission, not a reminder); it is reached from the vehicle Detail summary row (plan 03-05). This plan implements the two-case tap on both placements.

**Android honesty, and the one file the artifact table does not enumerate.** `NotificationPermission.NOT_DETERMINED` cannot be observed on Android (03-07's KDoc), so the persisted `hasRequestedSystemPrompt` bit — written immediately **before** the prompt and never cleared — is the only thing that distinguishes "never asked" from "denied". It is written before the prompt on purpose: a process death during the OS sheet must not produce a second ask. A **second** bit, `hasAutoExplained`, records that the automatic post-save explanation has already been shown once; it is written when the dialog is presented (not when it is dismissed), so even a process death on the dialog cannot buy a second automatic ask. Keeping the two facts apart is what lets the surface stay visible after a denial while the automatic dialog never returns. The coordinator, its UI state and the pure policy live in one additional file, `NotificationPermissionCoordinator.kt`; the phase artifact row summarizes the seam as "requester (expect), both actuals" and does not enumerate every common helper (it also omits `AppModule.kt` from plan 03-06, which that plan edits). Splitting the lifecycle re-read across the two screens would duplicate the ON_RESUME contract and let them disagree — the exact failure D-61's "re-checked on every foreground" is meant to prevent.

Output: `commonMain/.../notifications/NotificationPermissionRequester.kt` (+ both actuals), `NotificationPermissionStore.kt` (+ both actuals, two bits each), `NotificationPermissionCoordinator.kt` (UI state, policy, coordinator, `LocalNotificationPermissionCoordinator`, `rememberNotificationPermissionCoordinator`), `FirstReminderAskSignal.kt`, `ui/reminders/components/ReminderStatusRow.kt`, `ui/reminders/components/NotificationsPermissionDialog.kt`, the first-add publish in `ReminderEditViewModel`, the one-shot flag in `RemindersViewModel`, the dialog host and inline row in `RemindersScreen`, the banner in `VehicleListScreen`, the coordinator + provider + foreground refresh in `App.kt`, and four `commonTest` suites (two new, two extended).

## Design notes locked before execution

**One requester, one store, one coordinator, provided once.** The requester is a plain common class with `request(onResult)` — not an `expect class` — because only the *factory* needs a platform (`rememberLauncherForActivityResult` on Android, `UNUserNotificationCenter` on iOS). `@Composable expect fun rememberNotificationPermissionRequester(scheduler)` is the only platform entry point; the two actuals are the only files in the app that touch a launcher or `requestAuthorizationWithOptions`.

**The callback reports the scheduler's state, not the OS boolean, and a grant re-enters delivery.** On Android the runtime result can say "granted" while app-level notifications are switched off (`areNotificationsEnabled()` is the second switch), so both actuals read `scheduler.permissionState()` after the platform callback and pass that. It is one extra suspend call for a permanently honest answer, and it means the UI never has to reconcile two sources of truth. When that state is `GRANTED`, the coordinator calls `scheduler.evaluateNow()` before `onSettled()`: plan 03-07's `evaluateAndDeliver` refuses to write either marker without permission, so the pre-dialog sweep was harmless and this post-grant sweep is the one that arms and delivers the cycle it skipped. `evaluateNow()` is fire-and-forget by contract, so the callback never waits on delivery and a dismissed dialog cannot cancel it.

**The store holds two bits, not a session flag.** `SharedPreferences` (`"notification_permission"` / `"system_prompt_requested"` + `"auto_explanation_shown"`) on Android, `NSUserDefaults` (`"vehicare.notification.system_prompt_requested"` + `"vehicare.notification.auto_explanation_shown"`) on iOS. The first is written before the prompt; the second when the automatic dialog is presented. Neither is ever cleared. Uninstalling clears both — which is correct, because a fresh install legitimately gets one fresh ask.

**`null` in the coordinator means "not read yet", and every surface is hidden while it is `null`.** The coordinator is the only reader of `permissionState()` outside the scheduler's own actuals; screens read the derived state. The initial read is explicit (`LaunchedEffect(Unit)` inside `rememberNotificationPermissionCoordinator`) rather than relying on `LifecycleEventEffect`'s observer replay, and the foreground re-read rides inside plan 03-07's **existing** `LifecycleEventEffect(ON_RESUME)` block — `App.kt` keeps exactly one such effect, because a second one would evaluate delivery twice per resume on Android (it would enqueue a second unique-work call) and would be a lie on iOS.

**The signal is replay-1, like `NotificationTapBus`, and only an add publishes it.** The editor publishes, then pops. The Reminders screen's ViewModel is alive in the back stack and would normally receive a replay-0 emission — but if the user backs out of Reminders while the save is in flight, the ViewModel is cleared and the ask would be lost. Replay-1 preserves it for the next matching Reminders screen; `consume()` is mandatory or a stale ask would reopen the dialog on every later visit. An **edit** publishes nothing: D-54's amended wording is "the first successful add", so the editor's `ruleId == 0L` is the only path that touches the signal. Whether the dialog then appears is still the policy's call — the signal says "a reminder was just added", never "ask now".

**The dialog's copy is fixed, not parameterised.** `ConfirmDeleteDialog` takes strings because it serves several delete subjects. There is exactly one permission message in this phase, so `NotificationsPermissionDialog` resolves `dialog_notifications_title`, `dialog_notifications_message`, `action_turn_on` and `action_not_now` itself. A caller cannot invent copy, and a second dialog with different words cannot be built without editing this file.

**Icons.** `NotificationsOff`, `Alarm`, `Timer`, `Schedule` and `Speed` are not in `material-icons-core:1.7.3`; the UI-SPEC's leading glyph is `Icons.Filled.Notifications` (the same one the Reminders empty state uses), and the chevron is `Icons.Filled.KeyboardArrowRight`. Both are decorative (`contentDescription = null`) because the row's text carries the meaning.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OS permission state → app | A value the app does not control, readable only by asking the platform; it can change while the app is backgrounded. |
| app → OS permission prompt | The one irreversible, one-time interaction in the phase; it can be spent and cannot be re-shown after a denial. |
| persisted permission bits → askability | Local storage decides whether the app believes it has already asked, and whether the one automatic explanation is already spent; a wrong value changes whether a prompt is ever offered. |
| editor save → Reminders screen | An in-process, cross-screen event carrying a vehicle id, with no user gesture in between. |
| screen → coordinator | A single shared instance; a screen reading the scheduler directly would bypass the askability gate. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-34 | Spoofing | permission state | mitigate | Only `NotificationPermissionCoordinator` calls `scheduler.permissionState()`; screens read the coordinator's derived state. A grep gate fails the build if `permissionState()` appears under `ui/` or in `App.kt`, so a screen cannot show or hide a surface from a second, staler read. |
| T-03-35 | Tampering | askability gate | mitigate | `NotificationPermissionPolicy` is a pure, exhaustively `when`-based object with a test per truth-table row; `requestPermission` re-checks `isAskable` and holds a single-flight flag, so a double tap or a recomposition cannot spend a second prompt or ask after a denial. |
| T-03-36 | Repudiation | permission surface copy | mitigate | The component resolves only `notifications_off_title` plus one of the two sanctioned bodies; the dialog resolves only its four sanctioned strings and takes no copy parameters. No literal is introduced, so the surface cannot drift from the UI-SPEC. |
| T-03-37 | Denial of service | repeated asks / prompt fatigue | mitigate | Two persisted bits, neither ever cleared: `hasRequestedSystemPrompt` (written before the OS prompt) and `hasAutoExplained` (written when the automatic dialog opens). `shouldAutoExplain` is false the moment the second bit is set, so **`Not now` ends the automatic ask for the life of the install** — later adds and every edit are silent — while `DENIED` with the system-prompt bit set is not askable, so a real denial ends the dialog permanently. Android has no `NOT_DETERMINED`, so the first bit is the only thing standing between the user and an ask on every add; the second is the only thing standing between the user and one ask per add. |
| T-03-38 | Tampering | cross-vehicle ask signal | mitigate | `FirstReminderAskSignal` carries a vehicle id and `RemindersViewModel` consumes only a matching id; the non-matching case is asserted to leave the bus value intact, so a save on one vehicle cannot raise a dialog on another. |
| T-03-39 | Elevation of privilege | coordinator bypass | mitigate | `LocalNotificationPermissionCoordinator` is provided once in `App.kt`; the requester and store are `internal` to `:shared` and referenced only by the coordinator's factory.
