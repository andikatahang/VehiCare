# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Stack:** Kotlin Multiplatform + Compose Multiplatform 1.12.1, **Material 3 only** (`material3:1.12.0-alpha03`).
> shadcn / Tailwind / Radix are **not applicable** — the shadcn initialization gate does not apply to this project (KMP, not React/Next/Vite). No component registry is used.
> **Scope of this document:** the visual and interaction contract for the shared (`commonMain`) UI of the Service Log. It **carries forward the Phase 1 design system unchanged** (tokens, states, copy rules) and adds no colour, type size, weight or spacing value that Phase 1 did not declare.
> **Binding upstream inputs:** `02-CONTEXT.md` D-23…D-40 (user decisions, binding) · `02-RESEARCH.md` (verified stack + discretion calls) · `01-UI-SPEC.md` (approved Phase 1 tokens and rules) · `01-PATTERNS.md` (binding conventions) · D-01…D-22 carry-forwards.

## Typography

**Declared sizes: 4 (14, 16, 20, 24sp). Declared weights: 2 (400 Regular, 500 Medium). Nothing else may appear.** Carry-forward from `01-UI-SPEC.md` — Phase 2 adds no size and no weight; it only extends which declared role each surface uses.

| Role | Size | Weight | Line Height | M3 slot | Phase 1 use | **Phase 2 use added** |
|------|------|--------|-------------|---------|-------------|----------------------|
| Display | 24sp | 500 | 28sp (1.17) | `headlineSmall` (weight override) | vehicle name on the vehicle Detail | **the service type at the top of the Service entry detail's focal block** (one Display element per screen — see C-21) |
| Heading | 20sp | 500 | 24sp (1.2) | `titleLarge` (size override from 22) | top app bar title · dialog title · empty-state heading | "Service history" / "Add service" / "Edit service" / "Service entry" title bars · **"Add service type" dialog title** · **"No service entries yet" empty-state heading** |
| Title | 16sp | 500 | 24sp (1.5) | `titleMedium` | vehicle name on cards · form section label | **service type as the history-row title** · **cost as the history-row trailing value** · **section labels: "Service type", "Parts", "Photos"** · **"Service history" line in the summary row** |
| Body | 16sp | 400 | 24sp (1.5) | `bodyLarge` | text-field input · Detail values & meta · dialog/empty body · Snackbar text | `date · mileage` meta lines · history-row meta · entry-detail field values · entry-detail notes text · part lines (`name × qty`) · empty-state body |
| Label | 14sp | 500 | 20sp (1.43) | `labelLarge` | buttons · tab labels · plate chip · Detail field labels | entry-detail field labels · **all supporting lines** (mileage/kost previews, the mileage warning, the photo count, import errors — C-27) · "Add part" / "Add photo" text buttons · dialog buttons |

Notes:
- Body line height is **1.5**; Heading line height is **1.2** (unchanged).
- Hierarchy is **size + weight + tone** (`Ink` vs `Slate`), never colour (unchanged). `Slate` carries every secondary line: history-row meta, entry-detail field labels, the summary row's meta, the em-dash placeholder, supporting lines.
- The date display format is locked: **`19 Oct 2026`** (`day Month-abbrev year`) — the single display format for service dates, produced by the shared `ServiceDates.display` util, never re-formatted per screen.
- Numeric display formats are locked: mileage **`123.456 km`** (dot thousands separators + ` km`), cost **`Rp 450.000`** (dot thousands separators, no decimals, `Rp ` prefix). Both are pure-Kotlin formatters with unit tests — no locale APIs (D-29).
- M3's text-field label 0.75 scale animation remains a component transform, not a fifth size (carry-forward). M3's `bodySmall` 12sp is **not** an accepted default anywhere in this phase — supporting lines are explicitly styled to `Label` (C-27).
- The date-picker's own headline text is library copy and is not overridden; `showModeToggle = false` keeps the calendar-only form (the input-mode day/month/year fields would sit outside this type scale and the digits-only keyboard discipline).

## Visual Hierarchy & Focal Points

**Hierarchy statement:** every screen carries exactly **one** maximum-weight element, expressed through size, weight and tone only.

| Screen | Focal point | Second level | Recessive level |
|--------|-------------|--------------|-----------------|
| Service history — **empty** | the empty-state heading ("No service entries yet") stacked with the "Add service" CTA | empty-state body copy | the wrench visual above the heading |
| Service history — **populated** | the **first row's service type** (newest first by default); the FAB is the action anchor bottom-right | row meta (`date · mileage`) | the trailing cost, then the sort control above the list |
| Add/Edit service entry | the **first four field groups** (Service date → Mileage → Service type → Cost) — the "30-second path" block (D-30/D-31) | Notes, Parts | Workshop/Mechanic, Photos, then the submit button last |
| Service entry detail | the **service type** in the focal block (Display) | the `date · mileage` meta directly beneath it | field rows, then parts, then the photo strip, then the destructive action last |
| Vehicle detail (changed) | *unchanged* — the vehicle name | *unchanged* — hero photo | the new **Service history summary row** sits where the coming-soon slot sat: below the field rows, above the destructive button |
| "Add service type" dialog | the text field (the only input) | confirm/cancel row | dialog title |

Deleting a service entry is intentionally the **lowest** weight on the entry detail — last element, below a `2xl` 48px break, worded in plain language, reachable only through the confirmation dialog (D-35, mirrors D-18).

### Service-type chip group (D-26) — `ServiceTypePicker`

- `FlowRow` (verified present in foundation-layout 1.12.x), full width, `sm` 8px gaps on both axes. Order is locked: **the six presets → learned custom labels (newest-used first) → the "Add custom…" chip**.
- Each type option is a `FilterChip` with `Modifier.defaultMinSize(minHeight = 48.dp)`; the selected chip additionally shows a leading 16dp `Check` glyph (`contentDescription = null`) and takes the palette colours declared in §Color item 10. Unselected chips: `Mist` container, `Slate` label, `Hairline` border. M3 applies `Role.Checkbox` to chips (verified in the pinned `Chip.kt`), so selection is announced and never carried by colour alone.
- "Add custom…" is an `AssistChip` (leading `Add` glyph, `Mist`/`Hairline`/`Ink`) — visually an action, not a selection.
- The six presets are **constants in code** (`ServiceTypePresets.ALL`, D-23 order: Oil change · Tire rotation · Brake service · Inspection · Battery · Filters), **not** six string resources: the stored value and the displayed label are the same token (D-40), and duplicating them into `strings.xml` would create a second source of truth.
- Learned labels are user text (a resource cannot own them) and are filtered case-insensitively against the presets before rendering (D-24/D-25).
- The one-field prompt is a `Paper` `AlertDialog`: title "Add service type" (`Heading`), one `OutlinedTextField` (`singleLine`, label "Service type", max 60 chars, trimmed, no case transform), confirm `TextButton` "Add type" (disabled while the trimmed value is blank), cancel "Cancel". On confirm, the trimmed label is matched case-insensitively against presets and existing learned labels: a match **selects the existing chip** (no duplicate chip, and **no stored value is ever rewritten** — D-40); otherwise the new label becomes the selected chip and a candidate learned label.

### Add/Edit service entry — single scrolling form (D-08/D-30)

One `Column(Modifier.imePadding().verticalScroll(rememberScrollState()))`; `lg` 24px between field groups; `md` 16px between fields of one group; `3xl` 64px bottom padding so the submit button clears the keyboard and the last input. **No autofocus** — the fast path (D-31) needs no typing at all (the date is already today), and an auto-opened keyboard would cover the type chips that are the actual second tap. **No nested vertical scrolling** anywhere: parts rows and photo thumbnails are plain composables (the photo strip scrolls horizontally only).

Locked field order:

| # | Field / group | Control | Required |
|---|---------------|---------|----------|
| 1 | Service date | read-only outlined field (56dp) showing `19 Oct 2026`, trailing `DateRange`, tap → `ServiceDatePickerDialog` | **`*`** |
| 2 | Mileage | `OutlinedTextField`, numeric keyboard, digits-only, max 9 digits, label "Mileage" | **`*`** |
| 3 | Service type | `Title` section label "Service type" + the chip group | **`*`** |
| 4 | Cost | `OutlinedTextField`, numeric keyboard, digits-only, max 12 digits | — |
| 5 | Notes | `OutlinedTextField`, multi-line (`minLines = 3`, `maxLines = 6`), max 500 chars, no counter | — |
| 6 | Parts | `Title` section label "Parts" + inline part rows + "Add part" `TextButton` (starts with **zero rows** on add) | — |
| 7 | Workshop | `OutlinedTextField`, single line, max 120 chars | — |
| 8 | Mechanic | `OutlinedTextField`, single line, max 120 chars | — |
| 9 | Photos | `Title` section label "Photos" + strip or empty block + "Add photo" + count line (max 5) | — |
| 10 | Submit | full-width filled `Button` at the bottom of the same column — "Add service" / "Update service" | — |

Submission gate: the submit button is enabled **iff** a date is set, the mileage digits are non-blank, a service type is selected, and no save/import is in flight. Nothing else gates it (D-27/D-28).

### Service history — row anatomy and sorting (D-33/D-34)

- Sort control: `SingleChoiceSegmentedButtonRow`, **full content width**, two segments `Date` | `Mileage`, both **fixed descending** (newest date / highest mileage) — no direction arrow is rendered because the direction is not a user choice. Default is `Date` on every visit (ViewModel state, **never persisted**). Colours exactly as `VehicleTypePicker` (see §Color). `Modifier.defaultMinSize(minHeight = 48.dp)`.
- Control placement: `md` 16px horizontal padding, `sm` 8px above the first row; it renders **only in the Content state** (an enabled sort control over zero rows would be a dead control).
- Row (`ServiceHistoryRow`, a `Mist` M3 `Card`, 12dp radius, `md` 16px inner padding, merged semantics, tap → entry detail, **no long-press ever**):
  - title = the stored service type, `Title`/`Ink`, `maxLines = 1` with ellipsis;
  - meta = `19 Oct 2026 · 123.456 km` (`Body`/`Slate`, `sm` 8px below the title) — the middle dot `·` (U+00B7) with single spaces either side is the locked separator, same as the vehicle meta line;
  - trailing = cost `Rp 450.000` (`Title`/`Ink`), or the em dash `—` in `Slate` when the entry has no cost; vertically centred against the two-line column.
- List: one `LazyColumn`, `items(entries, key = { it.id })` — **keys are mandatory** (sorting reorders rows; PITFALLS CMP 1); content padding `md` 16px horizontal, `md` 16px vertical gaps, `3xl` 64px bottom (clears the FAB).

### Vehicle detail — Service history summary row (D-32)

- Replaces `ComingSoonSlot` **in place**: after the locked 48px break below the field rows, and the 48px break below it stays. `ComingSoonSlot.kt` is retired (deleted) with its string.
- `ServiceSummaryRow`: `Mist` container, 12dp radius, `md` 16px inner padding, min height 72dp, tappable (ripple), merged semantics. Row: `Column(weight 1f)` with the title "Service history" (`Title`/`Ink`) and the meta line (`Body`/`Slate`, `sm` 8px below) + a trailing 24dp `KeyboardArrowRight` in `Slate` (`contentDescription = null`).
- Meta line: `N entries · Last service 19 Oct 2026` when the vehicle has entries (plural resource — 1 entry / N entries), `No entries yet` when it has none. It is **navigation only** (D-32/D-36): no list, no add button, and it stays tappable at zero entries so the history screen's empty state (with its CTA) is reachable.
- While the aggregate is still loading, the row renders its title alone at a stable 72dp min height — no spinner inside a compact row.

### Service entry detail — read-only anatomy (D-35, order locked)

1. **Focal block** (top of content, `md` 16px top padding): the service type at `Display` 24sp/500 `Ink`, then the meta `19 Oct 2026 · 123.456 km` (`Body`/`Slate`, `sm` 8px below).
2. `lg` 24px break, then the field run in D-35's order:
   - **Cost** — `FieldRow` ("Cost" label, `Rp 450.000` value or `—`), divider below;
   - **Parts** — a `Title` section label "Parts" + one `Body`/`Ink` line per part, `name × qty` (e.g. `Oil filter × 2`), `sm` 8px between lines; **the whole block is omitted when the entry has no parts**;
   - **Workshop** — `FieldRow`, divider below, first of the run displaced by the Parts block when present;
   - **Mechanic** — `FieldRow`, divider below;
   - **Notes** — a **stacked** field variant (label `Label`/`Slate` above a left-aligned wrapping `Body`/`Ink` value, `xs` 4px gap), because a right-aligned wrapping value in a two-column row is unreadable; no divider below (last of the run).
   - Cost, Workshop, Mechanic and Notes **always render** with the em-dash placeholder for absent values (stable screen shape, C-2 carry-forward).
3. **Photos** — a `Title` section label "Photos" + the read-only 80dp thumbnail strip (`sm` 8px gaps, single horizontally-scrollable row, images decorative, **not tappable: no viewer ships this phase**); the whole block is omitted when the entry has no photos.
4. `2xl` 48px break, then the destructive `OutlinedButton` "Delete service entry" (full width, 48dp min, leading `Delete` glyph, `Danger` content colour, disabled while a deletion is in flight) — the **only** call site of the ViewModel's delete entry point, always through `ConfirmDeleteDialog`.

## States & Interaction Contract

Every screen implements these states explicitly. **No state may render a blank white area.**

| Screen | State | Required rendering |
|--------|-------|--------------------|
| Service history | Loading | Centred M3 `CircularProgressIndicator` on `Paper`, `contentDescription` = "Loading service history". No skeleton, no shimmer, no placeholder rows |
| Service history | Empty | `EmptyState`: 64dp `Mist` circle with a centred 24dp `Build` (wrench) glyph tinted `Ink` (`xl` 32px below), Heading "No service entries yet", body copy in `Slate`, then a **filled** "Add service" CTA. The FAB remains visible (D-36). The sort control is **not** rendered |
| Service history | Content | sort control + `LazyColumn` (keys mandatory), rows newest-first by the selected order, `md` 16px gaps, `3xl` 64px bottom padding |
| Service history | Error | Centred `Body` copy (load error) + an outlined "Try again" button. FAB stays visible; the empty state is **not** shown on error |
| Add/Edit entry | Idle | Normal form; submit enabled only when date + mileage + type are present |
| Add/Edit entry | Invalid | Inline error text appears **only** after the user has cleared a previously non-empty required text value (Mileage → "Enter the mileage." under the field, `Danger`); the service type has **no** error line — its `*` marker and the disabled submit button carry the requirement |
| Add/Edit entry | Mileage warning | When the entered mileage is lower than the baseline (the prefill on add; the immediately previous entry in Date order on edit), the field's supporting line is replaced by "Lower than the last recorded mileage — check this" in `Danger`. **Save is never blocked** (D-28) |
| Add/Edit entry | Uploading/importing a photo | All photo controls and pickers are disabled while an import or a save is in flight; every other field stays readable but disabled (Phase 1 `Saving` precedent) |
| Add/Edit entry | Saving | The submit button shows an M3 `CircularProgressIndicator` in place of its label; all inputs disabled (readable) |
| Add/Edit entry | Save failed | Form retained untouched, `Snackbar` with the save-error copy and a "Try again" action that re-invokes submit; the one-shot flag retires after the message (Phase 1 convention) |
| Add/Edit entry | Success | No celebratory animation. Add → pop back to the **history** screen (Flow-driven, the new row is already in order). Edit → pop back to the **entry detail** (streaming state already shows the change) |
| Entry detail | Loading | Centred progress indicator, `contentDescription` = "Loading this service entry" |
| Entry detail | Not found | `Body` copy "This service entry is no longer available." + an outlined "Back to service history" button that pops |
| Entry detail | Content | The locked order above; the destructive action disabled while deleting |
| Entry detail | Delete failed | Dialog already closed; `Snackbar` with the delete-error copy; **the entry stays on screen and stored** (no optimistic removal — Phase 1 convention) |
| Vehicle detail | (unchanged) | The summary row renders inside the existing Content state; its meta appears once the aggregate resolves |
| Any form | Back / abandon | Unsaved input is discarded by the back navigation **without** a confirmation dialog (Phase 1 precedent — the confirm dialog vocabulary stays reserved for stored-entity deletion). Photos persisted during the session are deleted on abandon per the established `persistedButUnsaved` rule; database-owned paths are never touched |
