## Phase Goal

**As a** vehicle owner, **I want to** log every service event — date, mileage, type, cost, notes, parts, workshop, and photos — and browse, edit, or delete any vehicle's full history, **so that** I have a trustworthy record of all maintenance performed.

<objective>
Close both UAT gaps at the interaction layer: make the service-type chip group multi-select (gap 2, user-approved scope expansion) and fix the invisible custom type (gap 1) by writing the confirmed label into both the selection and the chip list.

Purpose: 02-07 made several types storable and readable. This plan makes them enterable and visible. The GAP 1 root cause is precise: `onCustomTypeConfirmed` wrote only `values.serviceType`, while the picker renders `presets + learned`; a brand-new label therefore had no chip and the selection looked like it did nothing. The fix is structural — one pure transition returns both the next selection and the next chip list, so the two can never drift again — plus a defensive union in the picker so a selected label is always renderable even if the learned list is momentarily stale.

Slice position (MVP): this completes the create/edit half of the user story that 02-03 shipped, and the read half that 02-04/02-05 shipped. The display rule (one type as today, several joined by ` · `) is the last piece that makes a multi-type entry legible everywhere it is listed.

Output: `ServiceTypeSelection.kt` with the confirm/toggle transitions; list-shaped form values with an at-least-one gate; a multi-select picker and its call site; the ViewModel methods; `serviceTypeLine` plus its two call sites; the four new test files (two commonTest, one iosTest ViewModel test, one commonTest helper test); and the UI-SPEC + D-26 record corrections that document the approved override of the single-select rule.
</objective>
