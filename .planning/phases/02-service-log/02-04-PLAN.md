## Phase Goal

**As a** vehicle owner, **I want to** log every service event — date, mileage, type, cost, notes, parts, workshop, and photos — and browse, edit, or delete any vehicle's full history, **so that** I have a trustworthy record of all maintenance performed.

> **Roadmap fidelity note:** the ROADMAP `**Goal:**` line for this phase is outcome-form, not user-story form. The story above is a faithful restatement of ROADMAP success criteria 1–5 and REQUIREMENTS SVC-01…SVC-07 — no scope was invented. If the user wants the canonical story committed to ROADMAP.md, run `/gsd-mvp-phase 2`.

<objective>
Build the read-only Service entry detail destination and close the delete path end to end: the shared confirmation dialog both entities use, the entry detail ViewModel + screen, and the D-39 cascade that makes "delete a vehicle" genuinely cover its service log.

Purpose: deletion is the phase's only irreversible action, and it is the one place where a mistake is unrecoverable — a half-deleted entry leaves orphan child rows, and a half-deleted vehicle leaves the user's receipt photos on disk forever. This plan puts the whole destructive path (UI gate → transaction → file removal) in one auditable place, proven against a real database and a real filesystem.

Slice position (MVP): the "manage what you logged" half of the story — read one entry, edit it (the form landed in 02-03), delete it. Its destination is complete and registered here; the history row that opens it lands in 02-05, so the route is registered but unreferenced for one wave and no control anywhere points at a missing destination.

Output: `ui/components/ConfirmDeleteDialog.kt` parameterized and shared plus `ui/components/FieldRow.kt` moved unchanged (vehicle call-site imports updated; C-23), the entry detail screen + ViewModel, the cascade in `VehicleRepositoryImpl.delete`, and `ServiceEntryDeletionTest` proving rows, children and files all move together — including the vehicle→entries cascade.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user tap → irreversible data loss | The destructive button and its dialog are the only gate between a tap and permanently removed rows plus files. |
| parent row → child rows (vehicle → service log) | Foreign keys are never enforced on either platform; nothing but explicit code prevents orphan rows. |
| database rows → filesystem | Photo files outlive their rows unless the delete path hands every stored path to the deleter. |
| app → filesystem paths | Relative stored paths are resolved through the single `PhotoStorage` seam. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-04-01 | Tampering | `VehicleRepositoryImpl.delete` cascade ordering | mitigate | Children deleted before the parent inside one `transactionWithResult` (photos → parts → entries → vehicle); the test asserts zero orphan child rows after a vehicle delete, since FK enforcement is off (D-39). |
| T-02-04-02 | Information Disclosure | entry photo files surviving a delete | mitigate | The repository returns every photo path from the transaction and calls `photoDeleter` after it commits; the test asserts file non-existence on the real simulator filesystem for entry deletes and for the vehicle cascade (Pitfall 4). |
| T-02-04-03 | Repudiation | double-confirm enqueuing a second delete | mitigate | `deleting` is read as the single-flight guard at the top of `delete`; the destructive button is disabled while it is true; the test gates one call open and asserts the second never reaches the repository. |
| T-02-04-04 | Elevation of Privilege | a delete path that bypasses confirmation | mitigate | The dialog is the only call site of `viewModel.delete` and its KDoc (moved with the file) states the rule for both entities; `onDismissRequest = onDismiss` makes back/outside-tap/Escape all cancel. |
