## Phase Goal

**As a** vehicle owner, **I want to** log every service event — date, mileage, type, cost, notes, parts, workshop, and photos — and browse, edit, or delete any vehicle's full history, **so that** I have a trustworthy record of all maintenance performed.

<objective>
Close UAT gap 2 (a service entry must be able to carry more than one service type) at the data layer: ship schema v3 with a normalized `service_entry_type` child table, a v2→v3 backfill, an ordered list on the domain model, hydrating reads, transactional writes, and cascade deletes — then make every existing caller compile against the new shape.

Purpose: the user asked for several types per entry ("Saya juga mau input type bisa dipilih beberapa"). That request cannot be satisfied by the UI alone — the single `service_entry.service_type` column is the root cause. This plan builds the storage and repository half so plan 02-08 can build the multi-select form and the joined display rule on top of a stable, tested contract.

Why the legacy column survives: Android minSdk 26 ships SQLite 3.18, where `ALTER TABLE … DROP COLUMN` (3.35+) does not exist; rebuilding `service_entry` would rewrite its `sqlite_master` SQL (the table name gets quoted) and break the byte-identical migration-verify contract that `verifyCommonMainVehiCareDatabaseMigration` enforces. So `service_entry.service_type` stays as a NOT NULL **mirror of position 0**, written only from `serviceTypes.first()`, and this plan documents that decision in the schema file itself.

Scope boundary: the form keeps its single `serviceType: String?` field through this plan (only the two bridge functions change), so the picker and the edit screen compile untouched. Plan 02-08 replaces the form field, the picker and the display surfaces. The detail and history surfaces get a one-line temporary `serviceTypes.firstOrNull().orEmpty()` in this plan purely to keep the tree compiling; 02-08 replaces both with the locked `serviceTypeLine(...)` helper — do not invent a second display rule here.

Output: `ServiceEntry.sq` v3 + `2.sqm` + regenerated `3.db`; `ServiceEntry.serviceTypes`; mapper/repository/cascade changes with ordered hydration; the mechanical test call-site updates; a real-driver migration-backfill test and the multi-type repository/deletion tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| v2 database → v3 schema | An in-place upgrade touches every stored entry; a failed or partial backfill loses the user's type data. |
| form/domain → `service_entry` mirror column | Position 0 is written twice (child row and mirror); divergence makes old queries and new reads disagree. |
| entry id → child rows | Type rows are orphaned unless replace-on-edit and both delete paths are explicit (FKs are never enforced). |
| user label → learned chip list | Case variants can duplicate a chip, and a rewrite would violate D-40. |
| vehicle delete → service data | A missing type-row delete leaves personal maintenance data behind after the user believed it was erased. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-07-01 | Tampering | `2.sqm` vs `ServiceEntry.sq` DDL drift | mitigate | The table DDL is authored once and copied structurally into the migration; `verifyCommonMainVehiCareDatabaseMigration` plus the regenerate-then-`git diff --exit-code` pair are both run in Task 1 and re-run in the plan verification. |
| T-02-07-02 | Tampering | legacy entries losing their type on upgrade | mitigate | The backfill is `INSERT … SELECT id, 0, service_type FROM service_entry`, asserted row-for-row by `ServiceEntryMigrationTest` on a real driver. |
| T-02-07-03 | Tampering | mirror/child divergence | mitigate | The mirror is written only from `serviceTypes.first()` in one place (`toBindParameters`), and a repository test asserts both the child list and `selectById(id).service_type` after insert and after edit. |
| T-02-07-04 | Tampering | orphaned type rows after edit or delete | mitigate | Edit deletes then reinserts inside the same transaction; entry delete removes type rows before the parent; the vehicle cascade removes them before entries. All three paths are asserted. |
| T-02-07-05 | Information Disclosure | erased vehicle leaving service-type text behind | mitigate | `deleteTypesForVehicle` runs inside the same transaction as the rest of the cascade, and the cascade test asserts the survivor's rows are the only ones left. |
| T-02-07-06 | Tampering | duplicate learned chips from case variants | mitigate | `GROUP BY lower(label)` returns one row per case-insensitive label; a test uses `Wheel alignment` / `wheel alignment` across entries and expects one chip. |
| T-02-07-07 | Denial of Service | N+1 type reads on the history path | mitigate | History hydrates through one `selectTypesForVehicle(vehicleId)` query combined with the entry list; no per-entry query is added. |
| T-02-07-08 | Elevation of Privilege | foreign keys trusted to cascade | accept | SQLite FKs are declared for intent but never enabled; every delete is explicit SQL, so there is no reliance on enforcement. |
| T-02-07-SC | Tampering | npm/pip/cargo installs | accept | This plan installs no package and adds no dependency; it uses the committed SQLDelight toolchain. |
